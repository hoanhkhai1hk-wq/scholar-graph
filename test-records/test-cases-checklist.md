# 测试用例验收清单

建立日期：2026-10-24。维护方：WorkBuddy（前端、文档与跑测）。本文件只列「跑什么、怎么验、留什么证据」，不包含任何实现，也不包含已完成的实测结论。

## 使用规则

1. 每个用例的「实测结果」栏一律留空，由执行人在实际跑测后填写，禁止事前填写「通过」「OK」「符合预期」等任何结论字样。
2. 未填＝未执行，不等于通过。任何一栏为空的用例不得在汇报材料中宣称已验证。
3. 留证物按本节「留证物」清单逐项采集，缺项则该用例判定为「证据不齐」而非「通过」。
4. 填写人、填写日期、所用服务端 commit 哈希三项必须齐全，缺一则该条作废。
5. 本清单依赖 Codex 后端与解析管线先于跑测交付；依赖缺口见下节，不由本单自行实现或猜测接口行为。

### 需要用户转达总指挥的三处契约缺口

- **缺口 A（阻断用例一）**：五份契约没有「两篇论文为同一作品不同版本」的去重业务规则。`CONTRACTS.md` 写明「论文同名、DOI 相同与 PDF 字节相同是不同概念，v1 不定义去重业务规则」。因此用例一要验的「检出重合 / 建议保留新版」在 v1 里没有承载对象，需裁定：是复用 `PaperMeta` 已有字段判定，还是新增记录类型。
- **缺口 B（阻断用例一）**：「版本差异摘要」的输出不是 `QAAnswer`（它要求非拒答必须带论文锚点），也不是其余四类记录。需裁定其授予结构。
- **缺口 C（影响用例三）**：解析阶段、进度、错误与分页封装在 API 草案中标注「待裁定」。用例三要测的「流式解析不中断」依赖状态可观测，没有 `/parse-status` 的响应结构就没有读数口径。

以上三项在未裁定前，跑测只能记录实际发生的现象，不能据声称满足预期。

## 用例一：同一论文新版与旧版的去重与版本感知

**场景**：先后上传 arXiv `1706.03762` 的 v7 与 v1 两个 PDF，系统应基于内容而非文件名检出两者重合，给出预警、建议保留新版，并输出版本差异摘要。

**输入文件**：`fixtures/1706.03762v7.pdf`（先传）、`fixtures/1706.03762v1.pdf`（后传）。文件名与哈希见第五节登记表。

**前置条件**：第 0 节第 1、3、8、10、11、12 项均已交付并可在本地环境启动。

### 手工操作步骤

| 步 | 操作 | 观察点 |
| --- | --- | --- |
| 1 | 清空文献库，保证起始状态为空，截图列表页 | 列表为空，无残留记录 |
| 2 | 上传 `1706.03762v7.pdf`，记录返回的 `PaperMeta.id`、`file_hash`、`page_count`、`has_text_layer`、`version` | 五字段取值与契约一致；`version` 是否被识别为 `v7` |
| 3 | 等待 v7 解析完成，轮询 `GET /papers/{paper_id}/parse-status` | 状态序列可读，终态明确 |
| 4 | 查看 v7 的分块列表与参考文献条目，抽查页码上限不超过 `page_count` | `Chunk[]`、`ReferenceEntry[]` 可拉取 |
| 5 | 上传 `1706.03762v1.pdf`，记录返回值同上 | 是否生成新的 `PaperMeta.id` |
| 6 | 观察上传瞬间与解析完成后的两个时间点的界面表现 | 是否在同一时机出现去重预警；预警文案提及的判定依据是什么 |
| 7 | 触发预警后的推荐动作 | 是否有「建议保留新版」或等价措辞，是否可由人工否决 |
| 8 | 请求版本差异摘要（缺口 B 裁定后按其结构） | 摘要是否指向 v7 与 v1 的真实段落差异，是否给出路径/页码/分块定位 |
| 9 | 抽查摘要中至少 3 条差异，回到原文逐条比对 | 差异描述与原文是否一致，有无编造 |
| 10 | 人工否决一次「保留新版」，改为保留旧版，重看列表 | 系统是否尊重人工选择，是否仍保留两条记录 |

### 预期结果（验收标准，非实测结论）

- E1 两次上传产生两条独立 `PaperMeta` 记录，且 `file_hash` 不同。
- E2 系统在第二次上传后，不依赖文件名即可判定两者为同一作品的不同版本。
- E3 预警在界面可见，并说明判定依据（内容相似度／标题／DOI／arXiv 标识等实际用到的口径）。
- E4 给出保留新版的建议，且该建议可被人工覆盖。
- E5 版本差异摘要可定位到具体页码或分块，条目内容与原文一致。
- E6 整个过程结束时，两条记录均可被单独查看，未被静默合并或静默删除。

## 用例二：扫描版 PDF 的无文本层识别与 OCR 分支

**场景**：上传 `1706.03762v1_img.pdf`（扫描／图片型 PDF，无文本层），系统应自动检出 absence of text layer，切换到 OCR 分支完成解析，且 OCR 结果能进入问答与引用导航。

**输入文件**：`fixtures/1706.03762v1_img.pdf`。文件名与哈希见第五节登记表。

**前置条件**：第 0 节第 1、2、3、4、5、6、9、12 项交付完成；OCR 组件（DeepSeek-OCR 或 PaddleOCR）已接入并可调用。

### 手工操作步骤

| 步 | 操作 | 观察点 |
| --- | --- | --- |
| 1 | 用外部工具确认该 PDF 确实无文本层，记录判定方式与结果 | 形成外部基准，作为后续与系统判定比对的依据 |
| 2 | 上传该 PDF，记录返回的 `PaperMeta.has_text_layer` | 是否被自动判定为 `false`，而不是 null 或 true |
| 3 | 观察解析过程中是否走了 OCR 分支 | 有无可见的阶段提示或日志标记；若无任何可辨识迹象，则如实记录「不可观测」 |
| 4 | 轮询 `GET /papers/{paper_id}/parse-status` 直到终态 | OCR 分支是否比普通分支耗时显著更长，记录读数 |
| 5 | 拉取 `GET /papers/{paper_id}/chunks`，检查 text 是否非空 | OCR 文本是否落入 `Chunk.text`；是否有表格/公式按契约要求的来源标注 |
| 6 | 抽查 OCR 文本质量：随机取 5 个分块与原图逐行比对 | 字符错误率是否在可接受范围；公式区域是否被错误地编造成文字 |
| 7 | 对内容提问，取 `QAAnswer` | 回答是否引用了 OCR 得到的分块作为证据锚点 |
| 8 | 检查 `numeric_fact_check` 的 `checks` 项 | 数字类回答是否给出 passed/failed/unverifiable 及 evidence |
| 9 | 拉取 `citation-links`，从正文引用跳到文末条目再跳回 | OCR 是否损害了引用跳转链路；编号与条目是否对得上 |
| 10 | 对比有文本层版本与 OCR 版本在同一问题上的回答 | 差异是否可解释，还是 OCR 噪声导致的劣化 |

### 预期结果（验收标准，非实测结论）

- E1 `has_text_layer` 自动为 `false`，无需人工指定。
- E2 解析自动切入 OCR 分支，且在界面或日志中可辨识。
- E3 OCR 后的分块进入 `Chunk[]`，`text` 非空，`page_number` 与原文一致。
- E4 问答能基于 OCR 文本给出带 anchors 的回答，锚点指向 OCR 分块。
- E5 引用导航在此 PDF 上可用，正文与文末条目双向可达。
- E6 未把 OCR 置信度低的内容伪造成确定的原文表述。

## 用例三：长书 Understanding Deep Learning（541 页）的流式解析与分级加载

**场景**：上传 541 页长篇图书 PDF，解析不得中断；前端索引分级加载；阅读器懒渲染保证流畅。

**输入文件**：`fixtures/understanding-deep-learning.pdf`。页数按命题描述为 541 页，实际页数、文件大小与哈希见第五节登记表。

**前置条件**：第 0 节第 1、3、4、5、12 项交付完成；流式解析与前端懒渲染均已实现。

### 手工操作步骤

| 步 | 操作 | 观察点 |
| --- | --- | --- |
| 1 | 记录本机基准留证：CPU 型号、逻辑核数、内存容量、磁盘剩余空间、浏览器版本 | 用于后续数据可比性 |
| 2 | 开始上传并同步开始计时，记录上传完成时刻 | 上传耗时独立计量，不与解析混计 |
| 3 | 轮询 `GET /papers/{paper_id}/parse-status`，按固定间隔采样进度 | 进度是否单调推进，有无长时间停滞 |
| 4 | 全程采样服务端进程的内存占用（RSS）与 CPU，间隔 5 秒 | 峰值出现在哪阶段；有无持续增长的泄漏形态 |
| 5 | 观察解析是否出现中断、重试、超时或崩溃 | 任一异常即记录发生时刻与当时的页码 |
| 6 | 解析完成后核对 `page_count` 与实测页数是否一致 | 是否丢页 |
| 7 | 打开前端阅读器，测量首屏可交互时间 | 从进入页面到可翻页的耗时 |
| 8 | 打开全书导航树／索引，测量目录渲染耗时 | 541 页的目录是否需要分级加载而非一次性展开 |
| 9 | 快速连续翻页 100 页，采样帧率与卡顿 | 懒渲染是否生效；是否有白屏期 |
| 10 | 随机跳转至第 1、135、270、405、541 页，各测一次渲染耗时 | 不同位置的渲染开销是否均衡 |
| 11 | 同时打开 3 个页面标签，重复第 9 步 | 多实例并发下的浏览器内存占用 |
| 12 | 全流程结束后再等 5 分钟，采样服务端内存 | 是否有未释放的增长 |

### 预期结果（验收标准，非实测结论）

- E1 541 页全部解析完成，无中断、无重试导致的丢页。
- E2 解析过程中服务端内存无明显持续上升趋势。
- E3 前端导航／索引分级加载，未在首屏一次性渲染全部 541 页目录。
- E4 阅读器懒渲染生效，连续翻页无明显白屏或长时间卡顿。
- E5 `page_count` 与实测页数一致，最后一页可正常渲染。

### 放置与入库规则

1. 大文件**不进 Git**。仓库根 `.gitignore` 已忽略 `*.pdf` 与 `/data/`，`fixtures/` 只跟踪占位说明 `fixtures/README.md`。
2. 执行人将 PDF 从官方 `pdf/` 目录复制到 `fixtures/` 后，自行在本地使用，勿 git add、勿强推。
3. 文件名一律英文，不含中文与空格；与官方文件名不一致时在此登记「官方原名」。
4. 每个文件登记四项：文件名、页数、文件大小、SHA-256 哈希。
5. 哈希用本机工具计算：Windows 下执行 `certutil -hashfile "fixtures\<文件名>" SHA256`；Git Bash 下可用 `sha256sum fixtures/<文件名>`。取小写 64 位十六进制，与 `PaperMeta.file_hash` 同口径。
6. 若官方 `pdf/` 目录中的文件被替换或更新，必须重算哈希并更新本表，同时以「旧值 → 新值」形式记一行，不得直接覆盖。
