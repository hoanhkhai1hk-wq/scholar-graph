### 0.2 输入从哪来（重要）

- 没有真实解析管线，也没有接真实论文库。全部样例文本是我手工键入的，不是 PDF 解析结果，不是数据库检索结果。
- 样例里的两篇「论文」（paper-demo-fw-001、paper-demo-later-2024、paper-demo-cmp-2021、paper-demo-cmp-2023）是为实验虚构的样例，标题、年份、数值均为实验构造，不对应任何真实论文；报告任何地方都不声称它们是真实文献。
- 页码、section_path、chunk_id 是我按 contracts/chunk.v1.schema.json 的字段语义手工指定的（例如 chunk-fw-001-p7-001 表示 paper-demo-fw-001 第 7 页第 1 块），不是解析器输出，也没有 bbox。
- 因此文中的「锚点」在本次实验里检验的是「模型愿不愿意、能不能把一句话钉回给定文本的某个片段」，不是「真实 PDF 定位准不准」。

### 0.3 判读口径（按 contracts/ 现有 v1 与 v1.1 记录）

- QAAnswer（v1）：refused=false 时 anchors 至少一条；每个锚点四个必填字段 paper_id、page_number、section、chunk_id；数字陈述走 numeric_fact_check（passed / failed / unverifiable / not_applicable），passed 必须带 evidence。
- Chunk（v1）：chunk_id / paper_id / page_number / section_path / text 是回指的最小单位；section 必须对应 section_path。
- DedupDecision（v1.1）：evidence 每项只有 anchor + reason 两个字段；keep_new 必须用锚点说明新版相对旧版的优势。
- DiffSummary（v1.1）：key_sentences 每项 text + anchor + status；anchor 为 null 时 status 必须为 unverified，不许把无锚点的关键句写成有锚点。
- 三组实验都按这套字段口径设计；报告里没有自创契约字段，凡是模型自造的字段（例如「部分解决」）都在失败案例里点名。

写样例时刻意埋的几处（用于观察模型是否会被带偏）：

1. 样例 A 说「主实验结果以表格形式给出（本样例文本不包含该表格及其中的具体数值）」，全文没有任何数字指标 → 任何 F1 数字都只能是编的。
2. 样例 A 把跨语言、文档级、主动学习、噪声鲁棒性、推理效率、预训练模型结合都写成未来工作，其中前三个在样例 E 里被解决或部分覆盖，后三个没有。
3. 样例 C 明确写「没有复现 2021 年那类方法，因此无法在同等条件下直接比较」 → 任何「C 比 B 好 X」都是越界。
4. 样例 B 的指标是 MRR@10、样例 C 的指标是 nDCG@10，基线也不同（BM25 vs 纯稠密检索） → 直接比大小是口径错误。
5. 样例 B 的「50 万条查询—段落对、1:8 负采样」是 B 的数据，不在 A 里 → 把 12,000 条/ACE/2020 这类说辞安到 A 头上就是张冠李戴。

### 1.3 v1 结果与失败案例（跑了 2 次：37s / 25,659 tokens，40s / 32,130 tokens）

两次输出高度一致：都给出 6 条方向，与样例 A 原文的 6 个方向一一对应（跨语言、文档级、主动学习、噪声鲁棒性、推理效率、预训练模型结合），没有多抽，也没有把「多模态 / 强化学习 / 知识图谱」这类套话塞进来。状态标注为：跨语言=已解决、文档级=已解决、噪声鲁棒性=部分解决、主动学习=未解决、预训练模型结合=未解决、推理效率=未解决。

v1 第一次运行的原文（节选，未改动）：

```text
1. 扩展到文档级事件抽取，处理跨句事件论元分散问题，E 已报告同一框架可直接用于文档级抽取并处理该问题，状态：**已解决**。
2. 扩展到跨语言场景并检验零样本语言迁移表现，E 已在 12 种语言上验证，状态：**已解决**。
3. 进一步分析远程监督噪声下的鲁棒性，E 仅在跨语言子集上间接观察到相关表现，缺少独立消融分析，状态：**部分解决**。
...
仅依据样例 E，跨语言与文档级扩展已有验证，噪声鲁棒性证据有限，其余方向缺少完成证据；“未解决”不代表真实领域至今无人解决。
```

失败案例（v1）：

1. **零锚点，整份清单不可回指。** 6 条方向没有一条带 paper_id / page_number / section / chunk_id，也没有引文。按 QAAnswer、DedupDecision、DiffSummary 的锚点口径，这份清单无法落库，也无法判断某一条到底出自样例 A 的哪一句；下游只能整段重跑。这是本组最稳定的失败，两次运行都一样。
2. **状态判断无出处，且用了契约里没有的状态。** 「部分解决」不是任何契约的状态枚举（DiffSummary 只有 verified / unverified，DedupDecision 只有四种 recommendation），属于模型自造；而且「E 仅在跨语言子集上间接观察到」这句虽然确实在样例 E 里，v1 没有引出原文，读者无法核对它是引用还是概括。
3. **排除没有留记录。** 跨语言、文档级两条被标「已解决」后直接从路线图里消失，没有 excluded_by、没有被哪句话排除的说明。事后审计只能重跑，不能回答「为什么把这条删了」。
4. **把「更晚证据没做」和「更晚证据没提」混为一谈。** 两次运行的第 5 条都写成「E 未提供该方向的完成证据」「尚不足以判断更广泛的预训练模型结合是否完成」——同一句话既可能意味着方向仍开放，也可能意味着证据缺失，v1 没有把这两种情况分开，而这恰好是时间过滤最需要分开的地方。
5. **旁证（不纳入对比）：** 只给样例 A、不给样例 E 的那次运行，输出同样是 6 条方向、同样零锚点，但完全没有状态列——说明状态列是「给了更晚证据」才出现的，不是模型自发的锚点意识。

需要如实说明的一点：本组预期的「多抽套话方向」「把已解决的误留下来」这两个失败，在这两次 v1 里都没有出现。v1 的错不在抽得对不对，而在抽出来的东西**无法被核对**。

### 1.4 Prompt v2 原文（针对 1.3 的 1–4 条改写）

```text
你是一名论文信息抽取助手，本次输出必须遵守锚点纪律与时间过滤规则。

任务：从「样例文本 A」抽取作者自述的未来研究方向，再按时间过滤规则筛一遍，输出保留清单与排除清单。

硬性规则：
1. 每条保留的方向必须带 anchor，四字段齐全：paper_id、page_number、section（完整章节路径数组）、chunk_id；并附 quote，quote 必须是从该 chunk 原文中连续摘录的字符串（不超过 30 字），不得改写。
2. 无法给出 anchor 与原文 quote 的方向，一律不许进保留清单；如果它看起来像作者的意思但定位不到原文，只能写进「无锚点候选（不上清单）」，并写明判断理由。
3. 不许补充原文没有的方向；不许把领域通用套话（例如多模态、强化学习、知识图谱融合、可解释性）当成作者自述方向。
```

失败案例（v2，两次复现）：

1. **规则互相打架，导致漏项。** v2 规则 4 写明「更晚证据明确说未做/未纳入的方向，视为仍未解决，留在保留清单」，但两次运行都把「推理效率」「与大规模预训练语言模型结合」放进表 3 标 unverifiable。模型的理由是语义细分：E 只说「未评估推理延迟」，不等于整个效率方向没人做；E 只说「未接入指令微调的大语言模型」，不等于所有预训练模型结合都没做。这个理由本身不荒谬，但它让 v2 的保留清单从 v1 的 6 条掉到 1 条——**规则收紧的代价是召回骤降，而不是幻觉等比例下降**。
2. **锚点塞进表格单元，结构不可机读。** 因为 prompt 只要求「四字段齐全」，没规定输出结构，两次都把锚点写成 JSON 字符串塞进 Markdown 表格格子里。人能读，程序不能直接 parse，等于把锚点降级成了文本装饰。
3. **同一状态两种写法。** 第一次写 status=unresolved，第二次写「仍未解决」；prompt 没有给闭集枚举，模型每次自己造一个。
4. **「部分解决」被彻底删掉了。** v1 会给「部分解决」，v2 只有 open / excluded / unverifiable 三个去处，噪声鲁棒性这种「有间接观察但没单独做」的情况被硬塞进 unverifiable，丢失了「做了一半」这个信息。
5. **无锚点候选表永远为空。** 两次都写「无锚点候选：无」。这本身不算错（6 条方向确实都能定位），但也说明表 3 实际承担的是「判断不了」的回收站，而不是「抽出来但定不了位」的检查位。

### 1.6 结论与给 Codex 的落码建议

- **方向粒度要先定义，否则规则 3（不许补充原文没有的方向）和规则 4（未做=仍未解决）必然打架。** 本次 v2 的漏项全部来自「一条方向 = 一句话」还是「一条方向 = 一个研究主题」没定。建议在 prompt 里直接规定：一条方向 = 原文一个分句，逐字对应；粒度由文本决定，不由模型归纳。
- **不可验证应该是保留项的一个 status，而不是独立一张表。** 本次 v2 把 unverifiable 挪出保留清单，直接造成 2 条方向消失。数据结构建议：每条方向一个对象，字段为 direction_text、anchor（四字段）、quote、status（open / excluded / unverifiable 三选一）、excluded_by（仅 excluded 时非空：anchor + quote + reason）。
- **抽取和过滤分两次调用。** 本次 v2 单 prompt 塞了 6 条规则，输出 41k tokens，仍然在规则 4 上翻车；拆成「先抽带锚点清单（不判状态）→ 再对每条单独判时间状态」更稳，第二步每次只看一条方向 + 样例 E。
- **给 Codex 的接口**：FutureWorkItem 直接复用 Chunk 四字段锚点，不要新增字段；excluded_by 复用同一个锚点结构 + reason，和 DedupDecision.evidence 的 anchor + reason 口径一致；status 用闭集，禁止「部分解决」这类自造值。

4. **否定性论断靠运气。** C 恰好自己写了「没有复现……无法直接比较」（E13/E14），所以 S9/S10 站得住；如果换成「B 没有报告索引体积」这类缺席事实，证据表无处可引——prompt 没有定义这种情况怎么办，本次也就没有暴露。

### 2.6 结论与给 Codex 的落码建议

- **两段式确实压住了「先结论后补证据」，但压不住「引用不相干的证据」。** 要补一道支撑性校验：综合句引用的每个 E 行，其 quote 里必须出现该句的主语、比较对象或数值；不满足就降级为不可验证。这条靠 prompt 写不死，得用第二次模型调用或规则校验。
- **证据表以 chunk 为单位，不要以句子为单位。** 一行一个 chunk_id，配 quotes[] 数组；否则「证据条数」这个指标会被同一分块切碎而虚高，去重也麻烦。
- **缺席事实单独定义。** 「某某没做/没报告」只能引用原文的否定句，或标 not_reported，不许用「没找到」当证据。本次 C 的自述句恰好覆盖了这种情况，属于运气好。
- **给 Codex 的接口**：证据表输出 JSON（evidence_id、anchor 四字段、quotes[]、fact），综合句输出 { text, cites: [evidence_id], verdict }；程序侧检查 cites 非空、存在于表内、且 quote 命中；与 DiffSummary.key_sentences 的 text + anchor + status 口径对齐，无锚点一律 unverified。

## 4. 三组共性结论：推荐 Codex 采用的 Prompt 模式与 Guardrails 清单

### 4.1 三组实验里反复出现的三件事

1. **模型默认不锚点，只有被明确要求才写，写了也不一定写对位置。** 三组 v1 全部零锚点（第 1 组 6 条方向无一条带 chunk_id，第 2 组整段无锚点，第 3 组 9 题无一处出处）；第 3 组 v2 虽然每条都写了 chunk_id，但 numeric_fact_check 的 evidence 仍写成字符串。这三件事指向同一个结论：**锚点纪律属于结构约束，不属于措辞问题。** prompt 里的「必须带锚点」只能提高提及率，保不住字段类型与归属。

2. **规则收紧换来的主要是可审计性，不是幻觉率下降；代价是漏项。** 第 1 组 v1 抽到 6 条、v2 只保留 1 条（另外 2 条排除、3 条被错放进不可验证）；第 2 组 v2 从「1 段文字」变成「14 条证据 + 9 条综合」，可审计性上去了，但出现了「引用不相干证据」的新问题；第 3 组 v2 结构齐了，字段类型又破了。**收紧后的召回损失必须单独评估，不能拿「看起来更严谨」当收益。**

3. **「文本没写」这类否定性/缺席性论断，是当前三组里最薄的环节。** 第 1 组里「E 明说没做」被模型判成 unverifiable 而不是 open；第 2 组里「C 没复现 B」只能靠 C 自己写了一句否定句才引得到；第 3 组里「文本里没有这个前提」只能整体拒答。三处都不是模型编造，而是**没有一种被约定的表达方式去说「此处为空」**。

### 4.2 推荐 Codex 采用的 Prompt 模式

**模式 A：三段式流水线，而不是一条大 prompt。**

1. 抽取段：只输出带锚点的候选条目，不判状态、不写结论。输出 JSON 数组，每条 { text, anchor{paper_id,page_number,section,chunk_id}, quote }。
2. 校验段（程序，不是模型）：锚点四字段齐全、chunk 存在、quote 是 chunk 原文子串、数字能在 quote 里找到。
3. 判定/综合段：只接收通过校验的条目；每条输出 { verdict, cites[], reason }，cites 必须指向校验段留下的 evidence_id。

本次第 2 组 v2 已经是这个形状的两段，第 1 组 v2 是一条 prompt 里塞 6 条规则，结果后者在规则 4 上翻车、前者只在「支撑性」上翻车——**能拆就拆**。

**模式 B：一条 prompt 只压一条硬规则。**

第 1 组 v2 的失败可以直接归因到规则 3（不许补充原文没有的方向）与规则 4（未做=仍未解决）在同一条 prompt 里争夺解释权。建议每条 prompt 只保留一条不可协商的规则，其余放成示例。

**模式 C：状态用闭集，且给出反例。**

本次出现过「部分解决」「unresolved」「仍未解决」「unverifiable」四种写法。prompt 里应当直接给枚举与每个枚举的一句话定义，并各给一个正例一个反例。

**模式 D：证据表以 chunk 为单位。**

第 2 组 v2 把 4 个 chunk 切成 14 行，导致「证据条数」虚高、同一分块多锚点难去重。建议一行一个 chunk_id，配 quotes[]。

### 4.3 Guardrails 清单（建议 Codex 落成程序检查，而不是写进 prompt）

| 编号 | 检查项 | 触发动作 |
| --- | --- | --- |
| G1 | 锚点四字段齐全，chunk_id 存在于本次检索集合，page_number / section 与 Chunk 记录一致 | 不通过即丢弃该条，不让它进下游 |
| G2 | quote 是目标 chunk.text 的子串（去空白后比对），长度有上限，不许跨 chunk 拼接 | 不通过即标 unverified，不许改写成「近似引用」 |
| G3 | 每条综合句至少 1 个 evidence_id，且 evidence_id 必须在证据表内 | 缺失即标 unverified，不许留空当通过 |
| G4 | 支撑性检查：被引证据的 quote 里必须出现该句的主语、比较对象或数值 | 不满足降级为 unverified（第 2 组 S6 就是被这一条漏掉的） |
| G5 | 数字断言必须回到含该数字的 quote；不同指标（MRR@10 / nDCG@10）不许比较大小 | 违反即 failed，并在 numeric_fact_check 留痕 |
| G6 | 缺席性论断（某某没做 / 没报告）只能引用原文否定句，否则标 not_reported | 不许把「没找到」当证据 |
| G7 | refused 三态：answered / corrected_premise / refused，同一答案不许混用 | 混用即视为不合规输出 |
| G8 | 输出跑一遍 QAAnswer / DiffSummary / DedupDecision 的 JSON Schema，不通过就带错误信息重试一次 | 两次不过就返回错误，不静默降级 |
| G9 | 保留一份 v1 式自由抽取作为召回基线，v2 上线前对比条目数，跌幅超过阈值报警 | 用于发现第 1 组那种「6 条变 1 条」的回归 |
| G10 | 每次调用记录服务商、模型名、prompt 版本、耗时、token 数 | prompt 不当契约；模型换了要重跑，不能沿用旧结论 |

### 4.4 一句话给 Codex

三组实验里，模型答对内容的次数远多于答错的次数；真正反复出问题的是「答对但无法核对」。因此落码的重点不是把 prompt 写得更严厉，而是**把锚点、引用、状态做成结构字段，用程序校验兜住，prompt 只负责告诉模型该填哪些字段**。

## 5. 复现方式与已知局限

### 5.1 复现命令

每次调用都是同一形状（prompt 从 stdin 进，最后一条消息写到 -o 指定的文件）：

```text
codex exec --skip-git-repo-check -C <工作目录> -o <输出文件> -
```

- 模型与 provider 由 CLI 启动横幅打印（model: gpt-6.1-sol，provider: openai，reasoning effort: high），10 次纳入判读的调用一致。
- 每次都是新会话，没有 --continue / --resume，prompt 之外没有追加系统指令。
- 第 3 组 v1 的输出末尾出现过宿主技能追加的「D1–D12 交付终检快照」，不属于 prompt 效果，统计时已剔除，特此记录。

### 5.2 本次没有做的事（不要从本报告读出这些结论）

- 没有跑真实解析管线，没有真实 PDF、没有 bbox、没有真实论文库；页码与 chunk_id 是手工指定。
- 没有多模型对比，只有一个模型（gpt-6.1-sol）、10 次纳入判读的调用；同一 prompt 只复跑 1 次，不足以谈稳定性分布。
