# Prompt 链归档

建立日期：2026-10-24。建账方：WorkBuddy（前端、文档与跑测），供 DeepSeek Harness 与后续答辩材料取用。本文件是**空账本**，不含任何已完成的 Prompt 或验收结论。

## 一、这件档案干什么用

比赛材料需要回答一个问题：某个功能，到底是 AI 直接写对的，还是人一步步引导修正出来的。要能拿出证据，就必须把「原始需求 → AI 首版结果 → 发现的问题 → 引导修正的 Prompt → 终版结果 → 验收结论」整条链留下。事后补挂一两句自述，不具备证据效力，本表单不收。

两条硬约束：

1. **不许事后回填。每条记录在开发时随 git 提交同步补。** 首版结果当场存，不要等到功能验收完了再回想当时 AI 输出了什么。
2. **不许只留成功结局。验收结论只写实际发生的情况，包括「没有修好」「改用人工实现」「放弃该方案」在内。** 只写成功案例的链，等同于没有归档。

## 二、归档规则

### 规则 1：覆盖范围

每个**核心功能**至少留一条完整链。核心功能指：面向用户的、对结果有直接影响的、并且在技术文档中出现的功能。参考清单（不含工具类脚手架与纯数据搬运），当前项目至少包含：

- PDF 文本层判定与 OCR 分支切换
- 分块与章节标题提取
- 版本去重与版本差异摘要生成
- 参考文献抽取与双向引用跳转
- 带证据问答与数字事实校验
- 综述生成
- 推荐列表
- 结构化框架生成
- 图谱节点与边的构建
- CSV 图表生成

上述清单随实际实现增删，由总指挥在技术文档初稿校对时一并确认。

### 规则 2：一条链 = 一个功能的一次完整迭代

同一个功能如果在迭代中途发现方向错了并重新走过一遍，就再开一条新记录，在「验收结论」里写明前一条被弃用的原因。不许在同一个记录里反复覆盖，历史必须可读。

### 规则 3：同步时机

在对应功能的 git 提交**同时**补记录，并把该次提交的哈希填入「对应 git 提交哈希」。若一条链跨多次提交，则每次提交都补一行，用同一个「编号」串起来。哈希必须在提交后取真实值，不允许留 TODO 后补。

### 规则 4：原文原则

「AI 首版结果」与「引导修正的 Prompt」两栏填**原文**，不是概述，也不是「大概是这个意思」。太长就长那份文件里，在表内写「见 prompts/records/<编号>-raw.md」并在该文件存完整原文。二次加工过的文字不构成原始证据。

### 规则 5：空白含义

任何一栏为空，表示该项**没有发生或没有取得**，不代表该项为「无」。例如「发现的问题」为空，读作「本次未发现问题」，而不是「本次没有问题」，验收结论栏必须另行说明为什么没有问题。

### 规则 6：填写人与时间

「日期」为记录写入日期，不是功能上线日期。填写人写在「执行人」栏。两者缺一，该条记录无效。

### 规则 7：与本仓库其他文件的关系

- `docs/tech-doc-outline.md` 第 8、9 节的技术方案部分，一条一节引用本文件的链作为证据。
- `test-records/test-cases-checklist.md` 的实测结果不替代本文件的验收结论；反之亦然。前者回答「跑测是否通过」，后者回答「Prompt 迭代是否收敛」。
- 本文件由 WorkBuddy 建账，内容由 DeepSeek Harness 填充；归属不影响调阅，是否守规则由总指挥验收。

## 三、字段定义

| # | 字段 | 必填 | 填写说明 |
| --- | --- | --- | --- |
| 1 | 功能名 | 是 | 英文功能标识，与代码模块或接口端点对齐，例如 `pdf-text-layer-detect` |
| 2 | 日期 | 是 | 记录写入日期，`YYYY-MM-DD` |
| 3 | 原始需求 | 是 | 交给 AI 的第一句话，原文照抄 |
| 4 | AI 首版结果 | 是 | AI 第一次输出的内容，原文或原文存档路径 |
| 5 | 发现的问题 | 是 | 首版结果与实际要求之间的具体偏差，可多条；确实没发现则写明「本次未发现」并说明核查方式 |
| 6 | 引导修正的 Prompt | 是 | 针对上一步问题实际发出的下一句 Prompt，原文；多轮则依次编号列出 |
| 7 | 验收结论 | 是 | 通过／未通过／改用其他方案，并写明依据；禁止只写一个「通过」 |
| 8 | 对应 git 提交哈希 | 是 | 真实哈希，至少 7 位，与代码提交一一对应 |

附加字段（可选，填则须真实）：执行人、模型与版本、Milestone 或单号、备注。
